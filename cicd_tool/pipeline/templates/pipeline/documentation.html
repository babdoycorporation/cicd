Documentation

Everything you need to use and operate ReleaseRocket — from your first repository to production deployment.

Overview

ReleaseRocket is a self-hosted DevOps platform that combines Git hosting and CI/CD automation in a single application. Your team can host repositories, review code through pull requests, track work with issues, and ship through automated pipelines — entirely on your own infrastructure.

CapabilityDescription
Git hostingBrowse code, view diffs, edit files in the browser. Compatible with every standard Git client.
Pull requestsCode review with inline comments, approval rules, and merge protection.
Issue trackingLabels, milestones, assignees, and automatic closing from pull requests.
CI/CD pipelinesBuilds trigger on every push. Logs stream live to the browser.
Build agentsExecute builds on any Linux machine in your network.
Deployment targetsDeploy to Kubernetes, AWS, Azure, GCP, Docker registries, or SSH servers — one connector per target, no scripts.
OrganizationsGroup users, teams, and repositories under a shared identity.

Quick Start

1. Create a repository

Go to Repositories → New Repository. Enter a name (lowercase letters and hyphens, e.g. my-api), choose Public or Private visibility, and create it.

2. Create an access token

Open Profile → Personal Access Tokens, name the token, and generate it. Copy it immediately — it is shown only once. You will use this token as your Git password.

3. Push your code

Terminal
# Clone the empty repository
git clone http://your-server:8001/git/username/my-api.git
cd my-api

# Commit and push — use your token as the password
git add .
git commit -m "Initial commit"
git push origin main

4. Set up a pipeline

Add a rockerci.yaml file to the repository root (schema in the Pipelines section). Then in CI Dashboard, create a Project, an Application inside it, and a Pipeline pointing at your repository and branch. Every push to that branch now triggers a build automatically.

Core Concepts

The CI/CD side of ReleaseRocket uses a three-level hierarchy:

LevelPurposeExample
ProjectTop-level grouping, usually one per product or team. Holds environment variables, credentials, and notification settings.Acme Platform
ApplicationA deployable service within a project.auth-service
PipelineThe automated steps that run when code changes on a monitored branch.Build → Test → Deploy

Repositories (the Git side) and Projects (the CI/CD side) are related but separate: a pipeline pulls code from a repository to build it. This separation lets one project build code from several repositories.

Repositories

Browsing and editing

The repository page shows the file tree for any branch. Click a file to view it with syntax highlighting, or click Edit to modify it in the built-in Monaco editor and commit directly from the browser. Use Upload File to add files without a local Git client.

Cloning

Terminal
git clone http://your-server:8001/git/username/repo-name.git
# Username: your ReleaseRocket username
# Password: your Personal Access Token

Forking

Click Fork on any repository to create your own copy. Changes in your fork do not affect the original until you open a pull request back to it.

Stars and watching

Star a repository to bookmark it. Watch it to receive notifications for new issues, pull requests, and pushes.

Branch protection

Protect important branches at Repository → Settings → Branches. A protection rule can block direct pushes and require a minimum number of pull-request approvals before merging. Rules are enforced server-side — they cannot be bypassed from the UI or the API.

Pull Requests

Opening a pull request

  1. Push your feature branch to ReleaseRocket.
  2. Open Repository → Pull Requests → New Pull Request.
  3. Choose the source branch (your changes) and the target branch (usually main).
  4. Write a title and description, assign reviewers, labels, and a milestone as needed.
  5. Click Create Pull Request — or Create as Draft if it is not ready for review.

Reviewing

Reviewers can read the diff, add inline comments on specific lines (hover a line and click the + icon), and submit one of three review states:

ReviewEffect
ApproveCounts toward the required approvals for merge.
Request changesBlocks the merge until the author addresses feedback.
CommentFeedback only — neither approves nor blocks.

Merging

When the target branch's protection rule is satisfied (required approvals reached, no outstanding change requests), the Merge Pull Request button becomes available. Draft pull requests cannot be merged.

Issues & Milestones

Creating an issue

Open Repository → Issues → New Issue. Give it a one-line title and a detailed body (reproduction steps, expected behavior, screenshots). Add labels to categorize it, a milestone to schedule it, and assignees to own it.

Labels

Labels are repository-scoped and fully customizable at Repository → Labels. Each label has a name and a color. Typical conventions: bug, enhancement, documentation, good first issue, help wanted.

Milestones

A milestone groups issues toward a target — a sprint or a release. Set an optional due date; the milestone page shows completion progress as issues close.

Closing issues from pull requests

Include a closing keyword in a pull request description and the referenced issues close automatically when the PR merges into the default branch:

Pull request description
Closes #42
Fixes #17, Resolves #88

CI/CD Pipelines

Pipeline definition

Pipelines are defined in a rockerci.yaml file at the repository root:

rockerci.yaml
name: Build and Deploy

on:
  push:
    branches: [main, develop]

jobs:
  build:
    steps:
      - name: Install dependencies
        run: npm install

      - name: Run tests
        run: npm test

      - name: Deploy
        run: ./scripts/deploy.sh

Steps run in order on a build agent. If any step exits with a non-zero code, the run stops and is marked failed.

Environment variables

Every step automatically receives:

VariableValue
CItrue
CI_COMMIT_SHAFull commit hash that triggered the run
CI_BRANCHBranch name
CI_PROJECTProject name
CI_PIPELINEPipeline name
CI_RUN_IDUnique run identifier (UUID)

Custom variables are configured per project at Project → Configure → CI/CD Variables and injected into every step.

Run statuses

StatusMeaning
PendingQueued — waiting for a free build agent.
RunningSteps are executing; logs stream live.
SuccessAll steps completed with exit code 0.
FailedA step returned a non-zero exit code.

Handling a failed build

Open the failed run and expand the red step to read its console output. Fix the code or configuration and push again — a new run starts automatically. To re-run without pushing, use Trigger Build on the project page.

Builds remain Pending indefinitely if no agent is online. Verify at least one agent is live under Agents in the sidebar.

Access Tokens

Personal Access Tokens authenticate Git operations and API calls in place of your account password. Each token can be named and revoked independently.

Creating a token

  1. Open Profile → Personal Access Tokens.
  2. Name the token after where it will be used — laptop, deploy-script, vs-code.
  3. Click Generate Token and copy the value immediately.

The raw token is displayed once and never again. ReleaseRocket stores only a SHA-256 hash — a lost token cannot be recovered, only replaced.

Using a token

Terminal
# Interactive — paste the token at the password prompt
git clone http://your-server:8001/git/username/repo.git

# Scripted — embed in the remote URL
git remote set-url origin \
  http://username:TOKEN@your-server:8001/git/username/repo.git

Revoking

Delete any token from your Profile page. Access is denied immediately for all clients using it.

Organizations & Teams

Organizations group users and repositories under a shared identity — typically your company or department. Within an organization, teams (e.g. Backend, DevOps) provide finer-grained grouping.

  • Create an organization — Organizations → New Organization.
  • Add members — use the Add Member form on the organization page; select the team they join.
  • Create teams — use Create Team on the organization page.
  • Organization repositories — select the organization as owner when creating a repository.

Build Agents

Agents execute pipeline steps. Any Linux machine that can reach the ReleaseRocket server can be an agent — no dependencies beyond Python.

Starting an agent

On the build machine
python linux_agent.py \
  --server http://releaserocket-host:8001 \
  --port 9000 \
  --hash-key "your-secret-hmac-key"

Register the agent in the UI at Agents → Add Agent with the same host, port, and hash key. The agent sends a heartbeat every 30 seconds; if heartbeats stop, it is marked offline and receives no new jobs.

All server-to-agent requests are signed with HMAC-SHA256 using the agent's hash key. Requests with invalid signatures are rejected, so an exposed agent port cannot be used to inject jobs.

Deployment Targets

Deployment Targets let a pipeline push directly to cloud infrastructure or a remote server — without writing deployment shell scripts by hand. The worker detects a special deploy: command in a step and routes it through the right SDK/CLI automatically.

Supported connector types

TypeWhat it runs
kuberneteskubectl rollout restart deployment using a kubeconfig token
aws_ecsaws ecs update-service --force-new-deployment
aws_eksFetches kubeconfig via aws eks update-kubeconfig, then runs kubectl rollout restart
aws_lambdaaws lambda update-function-code --image-uri $IMAGE_URI
azure_aksaz aks get-credentials then kubectl rollout restart
azure_appserviceaz webapp restart
gcp_gkegcloud container clusters get-credentials then kubectl rollout restart
gcp_cloudrungcloud run services update --image $IMAGE_URI
docker_registrydocker build + docker push to the configured registry
sshSSH into the target host and runs ./deploy.sh in /app

Step 1 — Create a credential

Go to Credentials in the sidebar and add a new credential. Choose the Type that matches your cloud provider:

CloudCredential fields
AWSUsername = Access Key ID  ·  Token = Secret Access Key  ·  Extra: {"region":"us-east-1"}
AzureUsername = Client ID  ·  Password = Client Secret  ·  Token = Tenant ID
GCPToken = Service Account JSON  ·  Extra: {"project_id":"my-proj"}
KubernetesToken = full kubeconfig YAML
SSHUsername = remote user  ·  Password = private key content
Docker RegistryUsername = registry username  ·  Token = token or password

Step 2 — Create a Deployment Target

Go to Deploy Targets in the sidebar and click Add Target. Fill in:

  • Name — a human-readable label, e.g. Production K8s
  • Type — pick the connector type
  • Endpoint / Host — cluster API URL, registry hostname, SSH IP, etc.
  • Region — AWS/Azure/GCP region (e.g. us-east-1)
  • Namespace / Cluster — K8s namespace, ECS cluster name, resource group
  • Credential — select the credential you created in Step 1
  • Environment — optionally tag this target as production, staging, etc.

After saving, open the target's detail page and note its numeric ID in the URL (/deployment-targets/3/) — you need it in Step 3.

Step 3 — Add a deploy step to your pipeline

In your rockerci.yaml, add a step whose run (or command) is a deploy directive:

rockerci.yaml
stages:
  - name: Build
    steps:
      - name: Build Docker image
        command: docker build -t myapp:$CI_RUN_ID .

  - name: Deploy
    steps:
      - name: Push to Production Kubernetes
        command: deploy:kubernetes:3   # ← type:pk of the target

      - name: Update AWS Lambda
        command: deploy:aws_lambda:7

The format is deploy:<type>:<target_pk>. The worker detects this prefix, looks up the target, injects its credentials as environment variables, and runs the correct CLI command — no manual SDK setup needed on the build agent.

The target's detail page shows the exact command string to copy. Go to Deploy Targets → <target name> and read the How to use box.

Environment variables injected at deploy time

In addition to the standard CI variables, the connector injects all credential fields under a prefixed namespace:

Naming pattern
DEPLOY_<SERVICE_NAME>_USERNAME
DEPLOY_<SERVICE_NAME>_PASSWORD
DEPLOY_<SERVICE_NAME>_TOKEN
DEPLOY_<SERVICE_NAME>_<EXTRA_KEY>

For example, a credential named AWS Prod exposes DEPLOY_AWS_PROD_USERNAME (Access Key ID) and DEPLOY_AWS_PROD_TOKEN (Secret Access Key). Your own shell scripts in the same pipeline can reference these variables too.

The build agent must have the required CLI installed (kubectl, aws, az, gcloud, docker, ssh) and available on its PATH. ReleaseRocket generates the command — it does not bundle the SDKs.

Required environment variables

VariableDescription
DJANGO_SECRET_KEYCryptographic secret. Generate with secrets.token_hex(50).
REPO_BASE_PATHDirectory where bare Git repositories are stored.
CI_RUNS_DIRWorking directory for pipeline execution.

Nginx

nginx.conf
location / {
    proxy_pass http://127.0.0.1:8001;
    proxy_set_header Host $host;
    client_max_body_size 500M;   # large git pushes

    # Required for live build logs (SSE)
    proxy_buffering    off;
    proxy_cache        off;
    proxy_read_timeout 300s;
}

proxy_buffering off is mandatory. With buffering enabled, live build logs appear only after the run finishes.
